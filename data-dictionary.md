## 1. Purpose and Reading Guide

This document defines the eleven tables from [the logical ERD](database-design.md), including proposed types, nullability, keys and validation. It supplies the next SQL implementation blueprint. PK means primary key; FK means foreign key; UQ means unique. A dash means there is no additional key/default shown, not that validation is absent.

Use InnoDB with utf8mb4 and a consistent supported collation. All columns used together in foreign keys must have matching types, signedness and applicable collation. Validate the installed MySQL version before generating and executing the final SQL; WampServer may also expose MariaDB, which must not be assumed to be the selected database service.

## 2. Shared Conventions

- IDs are positive auto-incrementing BIGINT UNSIGNED values, except composite preference-table keys.
- Unknown data uses NULL or an explicit status; never fake zero scores, empty country codes or invented dates.
- The application validates all allowed-value vocabularies, numeric bounds, dates and permissions. SQL CHECK constraints will enforce compatible local invariants where supported.
- BOOLEAN is represented by MySQL's boolean-compatible storage; enforce values 0 or 1 in validation/constraints.
- Store instants in UTC using DATETIME(6), set database sessions consistently to UTC and convert explicitly at application boundaries. DATETIME does not carry timezone information itself.
- Use decimal arithmetic for numeric scores. Academic percentages are 0–100, CGPA_4 is 0–4 and CGPA_5 is 0–5. A known result requires a supported scale; a scale may be known while its result remains unknown.
- Password hashes are generated by a maintained facility; no raw passwords are persisted. Parameterized SQL is mandatory.
- Public registration cannot set role. Role checks and record ownership checks are application responsibilities, even with valid foreign keys.
- Parent deletion is restricted by default. Unsave deliberately deletes the owner's dependent readiness rows and saved association in one transaction. Profiles and qualifications are not deleted implicitly by unrelated operations.

## 4. Keys, Indexes and Cross-Table Constraints

| Table | Additional key/index plan |
| --- | --- |
| users | UNIQUE(email); normalize consistently before duplicate checks and inserts |
| applicant_profiles | UNIQUE(user_id) and foreign key to users; one profile per applicant account |
| qualifications | Index(profile_id); foreign key to applicant_profiles |
| test_results | Index(profile_id, test_type); multiple attempts are allowed, so this is not unique |
| profile_country_preferences | PRIMARY KEY(profile_id, country_code); foreign key to applicant_profiles |
| profile_funding_preferences | PRIMARY KEY(profile_id, funding_type); foreign key to applicant_profiles |
| scholarships | Index(publication_status, deadline_at_utc); index(target_degree, country_code); a provider/cycle duplicate check is an administrative validation, not a name-only unique key |
| eligibility_rules | Index(scholarship_id); several rules of the same type may exist if evaluated as AND conditions |
| scholarship_documents | UNIQUE(id, scholarship_id), supporting the composite child reference; index(scholarship_id) |
| saved_scholarships | UNIQUE(user_id, scholarship_id); UNIQUE(id, scholarship_id), supporting the composite child reference; foreign keys to users and scholarships |
| checklist_items | UNIQUE(saved_scholarship_id, scholarship_document_id); composite foreign keys to saved_scholarships(id, scholarship_id) and scholarship_documents(id, scholarship_id); matching indexes for both pairs |

The redundant-looking parent unique pairs are intentional: the composite foreign keys guarantee that a saved opportunity and a document requirement belong to the same scholarship. checklist_items.scholarship_id is a controlled consistency field, not a separate user choice. There is no need to add a third independent scholarship foreign key when the composite references already establish it.

Role restrictions across users and profiles/saved records cannot be expressed by a simple FK. Enforce those in service-level transactions. Archive scholarship records rather than hard-deleting referenced opportunities. No automated account-deletion workflow is part of the initial feature set.

## 5. Initial Vocabulary and Rule Parameter Contracts

All listed parameter objects are specifications, not real scholarship claims. Rules must represent the official requirement. Multiple mandatory rules combine using AND. An allowed-values list within one rule supports OR among its listed alternatives. Conditions that cannot be represented accurately must be recorded as unresolved rather than approximated.

| Rule type | Required parameter contract | Evaluation policy |
| --- | --- | --- |
| ACADEMIC_RESULT | required_level, minimum, scale | Match a relevant qualification at required_level and compare a known compatible result; no automatic conversion between percentage/CGPA scales. Unsupported equivalence remains unresolved. |
| NATIONALITY | allowed_codes: non-empty country-code list | Pass for an included known nationality; missing nationality is unresolved. Residency/territory exceptions are not inferred from nationality alone. |
| QUALIFICATION | allowed_levels: non-empty list, in_progress_allowed: boolean | Apply the provider's stated acceptable qualification levels and completion policy; do not assume every PhD requires a master's. |
| FIELD | allowed_fields: non-empty canonical field list | Compare the intended field for programme compatibility. Prior-discipline conditions must be separately supported or flagged for review. |
| AGE | maximum: integer, reference_date: ISO date, inclusive: boolean | Calculate completed years on the source-defined date; missing birth/reference date or ambiguous age wording remains unresolved. |
| TEST | test_type, score_scale, minimum; optional validity_months and reference_date | Check a known matching result and supported score scale. If validity_months is supplied, reference_date is required. Test exemptions/alternative combinations require an explicit supported interpretation; otherwise unresolved. |
| UNSUPPORTED | requirement_text: non-empty string | Mandatory NEEDS_REVIEW condition produces UNRESOLVED; do not execute stored text as code. |

Use interpretation_status=UNRESTRICTED only after confirming that the criterion imposes no restriction; its parameters may be an empty object with a source note. UNRESTRICTED is not a substitute for missing source information. The examples in database-design.md are illustrative; these contracts refine their key names. In particular, the qualification contract uses allowed_levels and academic rules identify the relevant qualification level.

Before enabling any test evaluator, verify and document its official reporting scale, permitted range and format for the relevant result. Test names alone do not establish compatible scores: changed formats or different scales must not be silently compared. Additional component requirements require supported explicit checks. OTHER or unverified formats are retained for context but remain unresolved. Exact test-recency date arithmetic and boundary cases must be specified and tested before enabling validity-period rules.

One qualification can satisfy a supported rule if it demonstrably meets it. With several potentially relevant qualifications, do not select an arbitrary record. A confirmed suitable record may pass the rule; if no record passes and a potentially relevant record is incomplete, the rule remains unresolved; return FAIL only when sufficient known information establishes failure. Record this reasoning in the explanation.

## 6. Activation and Deadline Invariants

Activation requires provider name, target degree, destination country, funding category, application cycle, official URL, verification time, precise deadline/timezone and an adequate reviewed rule set. Draft rows may omit these while data is being prepared. An opportunity may include explicitly unresolved conditions, but those must produce unresolved checks rather than an unqualified eligible result.

The proposed cutoff policy is: an ACTIVE opportunity is open only while current_utc is strictly earlier than deadline_at_utc. At or after the instant, it is closed. No silent end-of-day assumption is made when the official page gives only a date. Ambiguous cutoffs require administrator verification; the precise source interpretation must be documented before activation.

Editing eligibility rules resets rules_reviewed to FALSE and returns an ACTIVE record to DRAFT in the same transaction. It may be reactivated after review. Editing source-sensitive deadline information also requires verification. Existing saved associations remain linked to the original cycle and can display an unavailable/under-review label when appropriate. A deadline extension is an explicit verified update; a new cycle is a new record.

## 7. Checklist and Preference Semantics

- Display active document requirements for each saved opportunity, left-joined with that applicant's checklist status. Missing status rows display as not ready.
- New requirements therefore appear without creating readiness records for every applicant. Retired document requirements remain stored but are marked inactive.
- Readiness changes must check ownership and matching scholarship references. They do not upload a document or certify provider approval.
- Empty preference tables mean no preference has been expressed, not a failed eligibility condition. The scoring formula must define neutral handling; it remains pending.
- Country/funding preferences are soft preferences. Mandatory country-related eligibility restrictions, where applicable, belong in explicit eligibility rules or remain unresolved.

## 8. Changes Relative to the Logical ERD

This document adds full_name for registration, funding_description for accurate benefit presentation, and selected timestamps explicitly. test_results.score_scale is added to distinguish reporting formats and prevent incompatible comparisons. These are refinements of existing responsibilities, not new application modules. The ERD shows selected columns and remains a logical overview. A final schema review must update diagrams if structural relationships change.

EligibilityResult, RuleOutcome and Recommendation remain calculated objects. Do not create tables for the eligibility engine, factory, facade or controller. Immutable scoring configuration remains application configuration with a version; no scoring-configuration table is required initially.

## 9. Planned Schema Verification

When the SQL schema is created, verify:

1. Duplicate normalized emails, duplicate saves and duplicate preference pairs are rejected.
2. Invalid foreign-key references and cross-scholarship checklist combinations are rejected.
3. Known academic results respect their scale; invalid or incomplete test states are rejected.
4. Applicants cannot assign admin roles or write another applicant's records through backend endpoints.
5. Unsave removes its dependent readiness rows atomically; a failed operation rolls back.
6. Draft records can be prepared, but activation cannot bypass required metadata and reviewed rules.
7. Deadline equality, UTC conversion, missing dates and incompatible grading scales produce the documented behavior.

These checks have not yet been run against MySQL. Application-level validation checks require backend code, not only the schema.
